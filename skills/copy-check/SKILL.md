# UI 文案检查

只审 UI 文案。功能逻辑、样式、代码结构不在范围内。

## 确定检查范围

推断优先级：① 用户明确说明的范围，② 当前对话上下文（用户刚让你开发了什么页面、改了哪些组件），③ 以上都不明确时，主动询问用户。

## 只看对终端用户可见的文案

**在范围内**：界面字符串、i18n key 对应的值、placeholder、tooltip、label、按钮文字、空状态说明、错误提示、Toast 通知等——凡是会出现在用户屏幕上的文字。

**不在范围内**：日志、代码注释、数据库字段/审计字段、接口文档、开发者工具输出。这些面向开发者，不是面向终端用户，标准完全不同（日志越精确越好，注释跟着代码走），不在本 skill 的职责之内。

读懂上下文：这个文案出现在哪个交互节点，用户触发它时正在做什么事。

## 逐条检查四类问题

**1. 实现细节外泄**

文案里是否出现用户不需要知道的内部概念——存储服务商、底层模块名、技术方案名称、内部系统代号、接口名等。

Badcase：「正在上传到 OSS…」「调用集成服务失败」「配置项写入 ConfigMap 出错」「通过工作流引擎执行中」

用户应感知的是业务动作（上传、保存、配置、执行），不是底层机制。

**2. 冗余说明**

文案是否在解释一个视觉上已自明的操作，或把使用流程当说明书贴在界面上。

Badcase：在带图标的删除按钮旁写「点击此按钮可删除当前项目」；在文件上传区写三段功能介绍；每个输入框都加一行使用说明。

判据：去掉这段文案，用户还能不能自然完成操作？能去掉就去掉。

**3. 术语不一致**

同一个产品功能、对象或动作，在不同页面/组件中是否叫了不同的名字。

检查方法：把本次改动涉及的所有名词提出来，搜索其他页面/组件里的用词做对比。同一产品里「数字人」和「数字员工」指同一个东西——这就是问题。注意：不同名称不等于不一致，需结合产品上下文判断两个词是否真的指向同一个概念。

**4. 文案铺满界面**

每个角落都放了一小段话，整个页面变成文字密集的说明手册。只在用户真正需要引导的关键节点放文案，其他地方让视觉设计说话。

## 报告格式

列出发现的问题，每条给出：

- 问题类型（实现细节外泄 / 冗余说明 / 术语不一致 / 文案过多）
- 位置（文件:行号）
- 当前文案
- 建议文案或修改方向

如无问题，直接说「文案无明显问题」。不要为了有产出而凑条目。
