# 编写 Handoff（任务交接）文档

把"当前这场对话里发生的事"凝练成一份**自包含**的交接文档，让接手者无需翻看本对话历史就能续作。

## 唯一的写作前提：按"接手者是全新 AI、零上下文"来写

无论下游是 compact 后的自己，还是另一个全新 AI，都按**最严格的情形**写——读者不知道你们聊过什么。因此：

- 禁止"我之前提到的那个文件 / 上面说的方案 / 我们讨论过的"这类指代。一切自包含。
- 路径写**可点击的全路径**（`demo/lib/adapter/rpc.ts:79`），不写"那个 adapter"。
- ID、分支名、命令、工作空间码等**真值**直接写出来，不要让接手者去猜或重查。

## 核心原则

- **现状明说，别让接手者自己拼**：用一句话直接点出全局状态（什么能用 / 什么卡着），而不是把它散落在各段让接手者去归纳——明说的结论可直接采信，靠拼凑散落事实最容易漏前提、误判状态。（重点是"有且明确"，不必纠结放第几行。）
- **诚实标注状态**：严格区分**已验证/实测**、**未验证/假设**、**已知问题/卡点**。宁可写"这一步没测过"，也不要让接手者误以为它能用。（这是交接的生命线——一个被粉饰的"已完成"会让接手者在错误地基上盖楼。）
- **密度优先，不堆砌**：只写接手者**需要**的。能从仓库/git/已有文档读到的，给指针（文件路径、文档链接、命令）而不是复制全文。handoff 是为了省 context，别把它写成又一个 context 黑洞。同一事实别在多个块里复述全文——换视角时点到为止、块间互相指引即可。
- **下一步看情况写，写就写实**：接下来做什么，若你能合理判断，就给可执行动作（具体到命令、文件，别写"继续优化"这种废话）；若方向得用户拍板，别硬编一个假的下一步，留白即可。
- **记录决策与坑**：写下做过的关键取舍**及其理由**、踩过的死胡同、不要重走的弯路。这是接手者最难自己重建、也最值钱的部分。

## 工作流程

默认**一气呵成、全程不向用户提问**——主题、文件名、章节取舍都由你自行判断，直接写完落盘。

1. **自拟主题与文件名**：从任务内容提炼一个短主题词组（如 `user-cli-发布测试`），文件名固定为 `<主题>-handoff.md`。不要为此问用户。
2. **定保存路径**：存到**联合工作空间根目录**的 `docs/<YYYYMMDD>/<主题>-handoff.md`。**禁止写子仓库自身的 `docs/`**；即使 cwd 已 cd 到某子仓库，也写根目录的 docs/。日期目录先跑 `date +%Y%m%d` 取真值，别凭记忆填；目录不存在就创建。只生成文件，不动 git（不 add/commit）。
3. **盘点事实**：动笔前先核对真值，别凭记忆——
   - 改了哪些文件：在相关 git 仓库跑 `git status` / `git diff --stat`，列出真实改动与提交状态（已 commit / 未 commit / 已 push）。若所在目录不是 git 仓库，据实说明、跳过提交状态，别编造。
   - 任务目标与进度：回顾本对话的原始目标、已完成到哪一步、卡在哪。
   - 关键真值：ID、分支、工作空间码、应用 id、命令等，能查证的就查证。
4. **按下方提纲写**，保存到第 2 步的路径。
5. **自检**（见末尾清单），尤其确认"全新 AI 拿着它能否零上下文续作"。
6. **告诉用户文件路径**（改/建文件后必须列出路径）。

## 建议覆盖的内容（提纲，非模板）

不给死模板。按任务自由组织章节、自拟标题，只要把下面这些点说清楚即可；不适用的就不写，有特殊维度（如多环境对比）就自己加。

**几乎总该有的五块：**

- **一句话现状** —— 做到哪了、什么能用、什么卡着。放最前面。
- **背景** —— 这件事怎么来的、最终目标、不可违反的约束。
- **用户交代过什么（重点）** —— 用户在本对话里**亲口**给的、AI 无法自行推断的信息：业务背景、硬约束与禁区、口头给的真值（工号 / ID / 链接 / 环境名）、明确的偏好与决策、对中途方案的纠正。**尽量保留原话或贴近原话，别转译成自己的概括**。这是 AI 推不出来、只能靠人喂的地基，compact 或换 AI 后最容易丢、也最难重建——务必单独成块、写厚一点。
- **干了哪些事** —— 这场对话里实际做的动作，复合的：调研、实测、调试、跑了什么命令、对接了哪些服务、读了哪些代码、发现了什么——**不只是"改文件"**。按逻辑或时间顺序，每条点到为止，细节给指针。
- **改动的文件（若有代码改动）** —— 逐仓库列改了哪些文件、各自改了什么、提交状态（已/未 commit、已/未 push）。纯调研/实测没动代码就不写这块。

**按需补充（自行判断要不要写）：** 下一步（能合理判断就给可执行动作，方向该用户拍板就别硬编、留白即可）、关键真值（ID/分支/命令等，标实测）、关键决策与坑（取舍理由、踩过的死胡同、隐藏约束）、未完/卡点（卡在哪、谁能解）、常用核对命令（附"什么输出算成功"）。

格式上：章节标题不加数字编号，不放目录。开头可用一行引言注明写于何日、供谁接手、配套文档链接。

## 质量自检清单

写完逐条自检，不达标就补：

- [ ] **零上下文可读**：通篇没有"我之前/上面说的/我们讨论过"这类依赖本对话的指代。
- [ ] **现状明说**：全局状态（什么能用/什么卡着）有一句话直接写出来，不用接手者自己归纳。
- [ ] **状态诚实**：每个"完成"都标了是否已验证；未测/假设/卡点如实写出，没有粉饰。
- [ ] **用户原话留住**：用户亲口给的约束、真值、纠正、偏好单独成块，尽量原话，没被转译丢味。
- [ ] **做了啥说清**：干过的事（调研/实测/调试/改码…）都交代了；若动过代码，改过的文件都列了、提交状态写清了。
- [ ] **下一步不注水**：写了下一步就要具体可执行；方向该用户定的，留白也行，别硬编。
- [ ] **密度合格**：没有大段复制仓库里已有的代码/文档，用的是指针。
- [ ] **路径可点击**：文件引用是全路径（必要时带 `:行号`），不是模糊描述。
- [ ] **已落盘并报路径**：保存到 `docs/<YYYYMMDD>/<主题>-handoff.md`，并把路径告诉了用户。
