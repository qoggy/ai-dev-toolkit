# 编写设计文档

产出一份可评审、可落地的设计：每一项设计都能对应到具体的存储、代码、接口或界面改动。以下规则是硬约束，逐条落实。文档文件名必须用英文。

## 必写章节：「需要你处理的事项」

放在文档**开头**，单独成章。用户一定会逐条阅读并解决这一章，而不一定细看其余内容——把所有需要用户介入的点都收拢到这里，其他章节不要再零散夹带提问。

列出三类，每条独立、可直接回答，并按「字母+数字」编号（如 A1、B2、C1），便于用户对焦时直接引用：

- **需用户提供的信息**（编号 A）：设计依赖但当前缺失的事实（如线上表结构、外部接口契约、账号或权限）
- **需用户拍板的决策**（编号 B）：存在多个方案、取舍会影响后续实现的选择点——给出选项和你的推荐
- **需用户确认的风险**（编号 C）：可能影响生产、有兼容性隐患、或不可逆的改动

编号一经分配不再复用：条目移入「已确认结论」后，用户对焦的过程中新增的条目从该字母的最大序号往后接。

若确实没有任何需用户处理的事项，写明「无」，不要省略此章。

### 子章节：「已确认结论」

置于本章末尾。用户在对焦中提供了信息、拍板了决策、确认了风险后，把对应条目**从上面的待处理列表移到这里**。每条用 `- **编号**：<结论>` 的列表格式，只写用户定下来的结论本身，不复述原问题、不加确认时间之类的元信息。待处理列表里不留已解决的条目。

```markdown
## 已确认结论

- **A1**：插件名采用 `paw-general`。
- **B1**：允许任意登录体系，不做 BUC 专用适配。统一流程是 AI 发现需要登录后交给用户操作，再验证最终页面状态。
```

## 多轮修改保持全文一致（MUST）

用户会与你多轮对焦（含回答上面「需要你处理的事项」里的问题），你会据此多次修改文档。每次改动都以**整篇文档**为单位检查，禁止只改一处、留下别的章节引用旧设计：

- **改数据结构**：删除或重命名某张表 / 字段后，全文所有引用它的地方（流程、接口、落盘示例、分镜）一并更新或删除
- **改流程 / 链路**：调整某条链路的做法后，所有描述该链路的章节同步修正，不允许一处已改、另一处仍写老做法
- **用户答复了某编号条目**：把该条目移入「已确认结论」，并按结论改正相关设计章节
- 改完**通读一遍**，确认没有自相矛盾、没有指向已删除内容的悬空引用

## 内容硬性要求

### 存储数据结构必须可见（MUST）

涉及任何持久化存储时，数据结构必须给出**定义或示例，二者不可皆无**：

- **数据库建表 / 改表**：列出表名、字段（名 / 类型 / 含义），或直接给出 DDL；改表要写清对哪些字段做新增 / 修改 / 删除
- **落盘文件**：给出文件路径 + 内容示例（用真实样例，不要写「类似 xxx 的格式」）
- **缓存、消息体、配置项**：同样给出结构定义或示例 JSON

### git 改动定位到仓库和分支（MUST）

涉及 git 仓库改动时，写明每个仓库的**仓库名称**、**分支名称**和**基线**，基线包含 **commit hash**。

### 列全改动文件路径（MUST）

涉及文件改动时，列出**所有**受影响文件的完整路径（可不写改动行数）。

### 接口变更列清单（SHOULD）

涉及接口变更时，列出接口信息。HTTP 接口至少给出 **path + 接口描述**；建议补充 method、关键入参与返回。

### UI 变更列页面与分镜（SHOULD）

涉及 UI 变更时，列出**改动了哪些页面**及**每个页面的改动内容**。可用 HTML 画分镜图表达布局与交互。

## 禁止事项

### 禁止「分期 / 下一步」填充（MUST NOT）

除非用户明确要求，禁止写「二期做什么」「后续规划」「下一步计划」。设计范围内的事**要么做、要么不做**，不允许把本该做的挪到「二期」来凑内容。
