# Plainly：把刚才那段话讲到能看懂

对象是**上一轮 AI 输出**；用户指定了别的范围（某一节、某个词、某个结论）则以用户指定为准。

用户愿意读，只是读不懂。任务是换一种讲法把同一件事讲清楚，不是做摘要。

不引入上一轮没说过的新结论，也不借机开一轮新工作。但为了把话讲准而核对真值、确认某个说法对应哪段代码，可以再查一次。
核对时发现上一轮讲错了：先一句话点明哪句错、正确的是什么，再按规则重讲，不要把错的重讲一遍。

## 硬规则

### 1. 结论先行

第一句就是结论：问题的答案、方案的取舍、任务的当前状态（什么能用 / 什么卡着）。不用"总结一下""简单来说""以下是要点"开头，不先铺背景。

结论本身只是判断（没查实）：照样放第一句，后面紧跟一个括注写明确定度，如"（判断，未验证）"。不因为要标确定度就把结论往后挪。

上一轮回答了多件事：第一句给最影响下一步决定的那个结论，其余各占一条要点行。

上一轮**本就没有结论**（还在调查、方向待用户拍板），就直说"上一轮没得出结论，只有 A、B 两个待定选项"，不临场编一个结论充数。

### 2. 讲现象，不讲内部状态流转

问题、故障、影响一律按**「谁 + 在什么情况下 + 做了什么 + 得到什么结果」**讲。主语是用户或调用方，不是变量和函数。

- 这样写：用户离线时点保存，改动只留在本地；重连后被服务端版本覆盖，改动丢失。
- 不这样写：`isOffline` 为 true 时 `save()` 跳过 `sync()`，重连触发 `pull()`，`localDraft` 被 remote 覆写。

内部状态流转不是禁止出现，而是**降级为定位信息**：现象讲完，把函数名、`路径:行号` 挂在后面一句，供追代码用。

用户问的就是机制本身（"GC 为什么会 stop-the-world"）：机制就是答案，按步骤讲，主语可以是组件；但每一步都要跟一句"这一步为什么非做不可"，否则又退回成状态流转叙述。

### 3. 用词必须可锚定

**术语和概念名**只能来自三处，其余用日常词汇：

- **业界标准术语** —— 用原文或通行缩写：`LSP`、`GC`、`CI`、`OOM`。只在中文译名本身就是通行叫法时才用中文（如"垃圾回收"）。
- **用户在本对话里用过的词** —— 优先复用用户原词，哪怕它不够精确。
- **代码 / 仓库里的真实标识符** —— 写全名并带出处（`RpcAdapter#connect`，`demo/lib/adapter/rpc.ts:79`），让它能被搜到。

**禁止自造概念名，禁止把标准术语意译成自创中文。** 反例：把 LSP 讲成"代码智能"；把 Chromium 的 document commit 讲成"文档提交"（中文读起来像"交一份文档"）。读者认得原词，认不得这类直译。

拿不准某个词对方是否熟悉：用一句大白话说它干什么，或直接给英文原文，绝不发明一个"听起来专业"的中文词。宁可写 `LSP（编辑器与语言分析进程之间的协议）`。

上一轮那个自造词，重讲时**直接换掉**，通篇用新说法。用户点名问的就是这个词时，只在第一次出现处写一句「上一轮说的『X』其实是 Y」建立对应，之后一律用 Y。

### 4. 一句一事

一个句子只放一个动作和一个结果。名词化的说法还原成动词——"完成了对配置的加载"写成"读了配置"。嵌套定语不超过一层。

- 不这样写：在确认了由于缓存未命中导致的对下游服务的重复调用被限流拦截之后触发的重试风暴是延迟上升的主因之后，我判断修复点在 `gateway/limiter.ts:142`。
- 这样写：延迟从 200ms 涨到 3s，主因是重试风暴（判断，未验证）。链路是：缓存没命中 → 重复打下游 → 被限流拦掉 → 客户端重试 → 越滚越大。修复点在 `gateway/limiter.ts:142`。

### 5. 真值不许换成模糊描述

以下一律原样保留：数字与量级、文件路径（必要时带 `:行号`）、可直接复制的命令、ID / 分支 / 版本号 / 环境名、报错原文的关键片段。

判据：真值让重讲后的版本**可执行**——看完就能去改那个文件、跑那条命令。"对相关模块做了优化"做不到，`把 rpc.ts:79 的超时从 3s 改成 10s` 做得到。

### 6. 分清事实、判断与未知

每句都要能被认出属于哪一类，不许出现读者分不清是查实还是推测的写法：

- **事实** —— 查实的、跑过的、读过代码的。直接陈述，附真值。
- **判断** —— 自己的推断。标出来："我判断""看起来""大概是"。
- **未知** —— 没验证、没查、不知道。明说"这一步没测过""还不确定"。

反例：把"根因已经确定"和"修复写法还没确定"写进同一段，读者判断不出这段到底有多确定，只好反过来问"你究竟定位清楚了没"。

宁可写"根因确定了（已复现 3 次），修法还没验证过"，不要笼统写"问题已定位，正在修复"。

### 7. 说清下一步该干什么

读完要知道接下来干什么。这条最容易漏，漏了整段等于白读。按情形写：

- **AI 继续做** —— 写清下一个具体动作，不写"继续优化"这种空话。
- **需要用户做** —— 写"需要你……"，说清要什么：一个决定、一份数据、一次授权。
- **需要用户在选项间拍板** —— 独立一行写「**需要你决定**：A 还是 B」，每个选项跟一句后果。

**待拍板的事不许藏在段落末尾的疑问句里。** 埋在一段技术叙述后面的"你是否接受扩大到这个范围？"，读者认不出那是在请求批准。

确实没有下一步（做完了，或在等外部结果），就明说"这件事到这为止"或"在等 X"。

## 该画图的时候画图

只有三类内容值得配图，其余用文字：

- **调用链路、流程** → `flowchart`
- **时序** → `sequenceDiagram`
- **待用户拍板的决策** → 分支后果用 `flowchart`；方案对比用 Markdown 表格（对比是列维度，不是画关系，画成图更难比）

图是结论的辅证，不是结论本身——先用一句话文字讲清结论，再放图。图放不下的细节写在图外，不要往图里塞。

**判据：一眼看出关系。** 主干单向、节点十个上下。节点多到需要逐条追线，图就失去了对文字的优势——先砍支线只留主干；砍完仍超，改成文字分步描述。宁可一张只画主干的图加一句话补充例外，不要一张什么都画的图。

**mermaid 语法防错**：节点文案尽量短，换行用 `<br/>`；含中文、括号、引号的文案一律用 `["..."]` 包裹，否则渲染报错。

**ascii 图只用于极简单的线性链或目录树，且图内不放中文**——中文是全角，混在框线里必然撑乱列对齐，读起来比纯文字更累；中文只允许作为行尾标注出现在最右侧。

## 格式

在对话里直接讲，不落盘、不建文件。一句结论开头，需要时跟几条要点行、一张合格的图，结尾是下一步。不要重建成带多级标题的文档。
